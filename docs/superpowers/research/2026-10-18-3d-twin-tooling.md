# 3D twin tooling: what exists, what to borrow, what is overkill

Date: 2026-10-18. Method: WebSearch + WebFetch only, no code run, nothing installed.
Scope: the twin in `docs/superpowers/plans/2026-10-18-board-detection-and-twin.md` (Tasks 3 to 5): homography → focal → pose, cylinder silhouettes, per-square visibility, predicted vs observed change masks on a 128 × 128 crop, in a vanilla TypeScript + Vite + onnxruntime-web phone page.

## 1. In-browser 3D projection and silhouette rendering

**Cost of the job first.** The twin needs ~30 convex silhouettes (two projected ellipses + hull per piece) rasterised into a 128 × 128 `Uint8Array`, plus a depth order for visibility. That is ~30 polygon fills of ≤ 16 k pixels each per frame, i.e. well under 1 ms of scalar JS on a phone; the 3 × 3 homography and 3 × 4 projection are a handful of multiplies per point. Nothing here needs a GPU, and a GPU path adds a readback that costs more than the whole CPU job.

- **three.js** · full scene graph + WebGL2 renderer · browser · ~600 kB min core (not re-measured here) · MIT **[direct]** `https://raw.githubusercontent.com/mrdoob/three.js/dev/LICENSE` · mature (r16x, WebGL1 dropped since r163) **[direct]** `src/renderers/WebGLRenderer.js`.
  - Readback is the trap: `readRenderTargetPixels(renderTarget, x, y, w, h, buffer, ...)` is a synchronous `gl.readPixels`; `readRenderTargetPixelsAsync(...)` (same args) creates a `PIXEL_PACK_BUFFER` with `STREAM_READ`, issues `readPixels` into it, `fenceSync(SYNC_GPU_COMMANDS_COMPLETE)`, polls, then `getBufferSubData` **[direct]** same file. A forum thread reports the synchronous call "drops the frame rate considerably on mobile (android)" **[via search]** https://discourse.threejs.org/t/readrendertargetpixels-huge-latency-on-mobile/27170.
  - **Pattern worth copying (ID buffer, not colour masks):** `examples/webgl_interactive_cubes_gpu.html` gives each object an integer `id` vertex attribute (`Int16BufferAttribute`, `gpuType = IntType`), writes it from the fragment shader via `layout(location = 0) out int out_id;` into a `WebGLRenderTarget` with `type: IntType, format: RGBAIntegerFormat, internalFormat: 'RGBA32I'`, clears to `-1`, and reads it back with `readRenderTargetPixelsAsync` **[direct]**. One depth-tested pass over all 32 cylinders yields a per-pixel "which piece is in front" map, which is exactly visibility + silhouettes in one image. If the twin ever moves to the GPU, do this (one 128 × 128 integer target, one async read per stable frame), never 30 separate mask renders.
  - **Verdict: overkill** for Tasks 4 to 5. The CPU path in `twin.ts` is smaller than three.js's loader code, and the plan's `Mask` is 16 kB.
- **Babylon.js** · engine with ES6 tree-shakable packages · browser · large · Apache-2.0 **[direct]** https://github.com/BabylonJS/Babylon.js · mature. Same readback economics as three.js, bigger surface. **Verdict: overkill.**
- **Hand-rolled projection (the plan's `poseFromHomography` + `project` + hull fill)** · ~150 lines TS · browser · 0 kB · ours. The maths it needs is in the OpenCV tutorial source, not just the rendered docs: with X = (X, Y, 0, 1), `x = K[r1 r2 r3 t]X` reduces to `H = λK[r1 r2 t]`, so `K⁻¹H = λ[r1 r2 t]`, `r3 = r1 × r2`, scale fixed by normalising the first column, and the tutorial warns the quick solution "does not ensure that the resulting rotation matrix will be orthogonal" and recommends polar decomposition / SVD **[direct]** `https://raw.githubusercontent.com/opencv/opencv/4.x/doc/tutorials/features2d/homography/homography.markdown`. For an ID buffer on the CPU: fill each piece's hull with its index into an `Int16Array(128*128)` in back-to-front order (sort by camera-space z of the base centre); the result is the visibility map and all silhouettes at once. **Verdict: use.**

## 2. Camera pose from a planar homography in the browser

- **OpenCV.js (official 4.x build)** · wasm · ~13 to 15 MB unpacked as published (`@techstark/opencv-js` 5.0.0-release.1: 14,731,296 bytes, Apache-2.0; `@opencvjs/web` 5.0.0-release.2: 13,325,498 bytes, Apache-2.0) **[direct]** `registry.npmjs.org` · mature.
  - What the default whitelist exports, from `platforms/js/opencv_js.config.py` on `4.x` **[direct]**: calib3d → `findHomography, calibrateCameraExtended, drawFrameAxes, estimateAffine2D, getDefaultNewCameraMatrix, initUndistortRectifyMap, Rodrigues, solvePnP, solvePnPRansac, solvePnPRefineLM, projectPoints, undistort, fisheye_*`; video → `calcOpticalFlowPyrLK, calcOpticalFlowFarneback, findTransformECC, CamShift, meanShift, createBackgroundSubtractorMOG2`; imgproc includes `warpPerspective, goodFeaturesToTrack`. **Not exported: `decomposeHomographyMat`, `phaseCorrelate`.** `@techstark/opencv-js`'s `doc/cvKeys.json` confirms the same set at runtime (solvePnP yes, decomposeHomographyMat no, phaseCorrelate no) **[direct]**.
  - Minimal bundle: `platforms/js/build_js.py` builds `calib3d, dnn, features2d, flann, photo` ON and `gapi, ml, imgcodecs, videoio, highgui, stitching, ...` OFF by default; `--config <file>` sets `OPENCV_JS_WHITELIST` to a custom export list; `--build_wasm`, `--simd` (`-msimd128`), `--threads`, `--disable_single_file`, and `--build_flags="-s USE_PTHREADS=0 -Os"` are the documented knobs **[direct]**. Historical reports put a whitelist-trimmed wasm at ~2 MB (core + features2d) and a module-trimmed one at ~4 MB **[via search]** https://answers.opencv.org/question/229032/opencv_jswasm-is-too-large, https://answers.opencv.org/question/209264/opencvjs-smaller-package. Expect a custom calib3d-only build to need the Emscripten toolchain and a CI job; no one publishes one.
  - **Verdict: maybe, later.** `solvePnP` on 81 grid points would refine the pose better than the closed form, but that is a 2 to 4 MB download plus a 1 to 2 s wasm compile on a phone for a function we can replace with 40 lines of Gauss-Newton on reprojection error. Keep it out of the plan's "no new runtime dependency" budget unless Task 3's synthetic tests show the closed-form pose is not within the 2° elevation target.
- **js-aruco2** · pure-JS ArUco + POSIT (`new POS.Posit(modelSize, canvas.width)`, `posit.pose(corners)` → best/alternative `{rotation, translation, error}`) · browser · small · MIT **[via search]** https://cdn.jsdelivr.net/npm/js-aruco2@2.0.0/README.md. POSIT is a coplanar-POSIT for four marker corners with a known focal; it does not estimate focal length. **Verdict: maybe** as a reference for a coplanar-PnP fallback; not needed when we have 81 correspondences.
- **MindAR (`hiukim/mind-ar-js`)** · pure-JS planar image tracking, "borrowed from artoolkit", TensorFlow.js used only as a WebGL compute backend · browser · dev build "> 10 MB" · MIT · last commit 2024-01-16 **[direct]** https://github.com/hiukim/mind-ar-js. Its pose estimator is tied to its feature pipeline. **Verdict: overkill.**
- **homography.js (`eric-canas`)** · image warping by homography only, no decomposition or PnP **[via search]** https://github.com/eric-canas/homography.js. **Verdict: no.**
- **Focal length from vanishing points, reference implementation: fSpy** (`stuffmatic/fSpy`, TypeScript/Electron, GPL-3.0) **[direct]**. `src/gui/solver/solver.ts` (follows Guillou et al.) has `solve2VP`: computes the two vanishing points from line pairs, projects the principal point P onto the line through them (Puv), then `let fSq = FvPuv * FuPuv - PPuv * PPuv; if (fSq <= 0) return null; return Math.sqrt(fSq)`; `computeCameraRotationMatrix(Fu, Fv, f, P)` normalises the back-projected VP directions and takes their cross product for the third column; the principal point may also be the orthocentre of the three-VP triangle **[direct]** `https://raw.githubusercontent.com/stuffmatic/fSpy/develop/src/gui/solver/solver.ts`. This is algebraically the plan's `f² = −(v1 − c)·(v2 − c)` with `v1 = H·(1,0,0)ᵀ`, `v2 = H·(0,1,0)ᵀ`. Because fSpy is GPL, re-derive rather than copy; the formula is one line. For a side-on tripod the two VPs are far apart and well conditioned; the degenerate case is a near top-down view (both VPs at infinity → `fSq ≤ 0`), which the plan already returns as `null`. **Verdict: use as the reference to test against.**
- Alternative: `calibrateCameraExtended` is in OpenCV.js, so Zhang's method from a few shots of the empty board is possible **[direct]** (config file above), but it needs several views; a fixed tripod gives one. **Verdict: no.**

## 3. Learned 3D / pose / depth models

Common verdict: for a fixed tripod looking at a plane whose geometry we know exactly (64 squares), a learned pose or depth model answers a harder question than we are asking, at 100× the download. None runs usefully in a phone browser today.

- **VGGT (`facebookresearch/vggt`, CVPR 2025)** · feed-forward camera params + depth + point maps from 1..N views, "reconstructs a scene in less than 1 second" on a GPU · server (torch, CUDA; CPU only as a code fallback) · 1B params (`VGGT-1B`; 500M/200M "planned") · code "commercial-use-friendly" since 2025-07-29 excluding military; **original checkpoint non-commercial**, `VGGT-1B-Commercial` by application form · no ONNX mention **[direct]** https://github.com/facebookresearch/vggt. **Verdict: overkill.**
- **DUSt3R / MASt3R (`naver/dust3r`, `naver/mast3r`)** · pairwise 3D point maps / matching · server (CUDA; a CPU docker compose exists) · ViT-L encoder + ViT-B decoder, ~570M / ~690M params **[via search]** · **CC BY-NC-SA 4.0** for both, plus training-dataset licences ("mapfree ... very restrictive") **[direct]** both READMEs · no ONNX/browser. **Verdict: overkill, and non-commercial.**
- **Depth Anything V2 (`DepthAnything/Depth-Anything-V2`)** · monocular relative depth · Small 24.8M params **Apache-2.0**; Base 97.5M / Large 335.3M / Giant 1.3B **CC-BY-NC-4.0** **[direct]** · community ONNX port and a Transformers.js real-time webcam demo exist, Core ML checkpoints for V2 Small **[direct]**. Browser ONNX of Small is ~100 MB fp32 **[via search]**; no phone FPS published. **Verdict: overkill.** Relative depth on a textureless board gives nothing the homography does not already give exactly.
- **Depth Anything 3 (`ByteDance-Seed/Depth-Anything-3`, released 2025-11-14)** · any-view depth + **camera pose (extrinsics + intrinsics)** from one or more images · server · SMALL 0.08B and BASE 0.12B, METRIC-LARGE and MONO-LARGE 0.35B **Apache-2.0**; LARGE 0.35B, GIANT 1.15B, NESTED 1.40B **CC BY-NC 4.0**; prefer `-1.1` checkpoints; no ONNX/mobile mention; streaming mode "less than 12GB GPU memory" **[direct]** https://github.com/ByteDance-Seed/Depth-Anything-3. DA3-SMALL is the one learned model that could plausibly be exported to onnxruntime-web and would give an independent focal/pose estimate from a single tripod frame. **Verdict: maybe, offline only** as a one-off cross-check of `focalFromVanishing` in `eval/`; not in the app.
- **FoundationPose (`NVlabs/FoundationPose`)** · 6-DoF pose + tracking of a known object, model-based (CAD mesh) or model-free (reference views + NeRF) · server, CUDA, PyTorch3D/NVDiffRast, Docker recommended · **NVIDIA Source Code License** (code and data) · no ONNX/mobile; public weights "slight performance degradation" because diffusion-augmented data was withheld **[direct]** https://github.com/NVlabs/FoundationPose. Pieces are rotationally symmetric and sit on known squares, so 6-DoF per piece is meaningless here. **Verdict: overkill.**
- **WebXR depth sensing** · `immersive-ar` session with `requiredFeatures: ["depth-sensing"]`, `cpu-optimized` (`frame.getDepthInformation(view)`, `luminance-alpha` 2-byte buffer, `rawValueToMeters`) or `gpu-optimized` (WebGL texture); ARKit/ARCore named as the native backends; depth objects valid only inside that frame's rAF **[direct]** explainer https://github.com/immersive-web/depth-sensing/blob/main/explainer.md. Shipped in Chrome on Android via ARCore **[via search]** https://developers.google.com/ar/develop/webxr/arcore-comparison. **Safari on iOS/iPadOS has no WebXR at all; visionOS Safari exposes `immersive-vr`, and `immersive-ar` is reported non-functional** **[via search]** https://developer.apple.com/forums/thread/743655 and third-party 2026 status pages. It also requires leaving our `getUserMedia` page for an AR session, which breaks the fixed-tripod capture loop. **Verdict: no.**

## 4. Scene reconstruction (Gaussian splatting / NeRF)

- **gsplat (`nerfstudio-project/gsplat`)** · CUDA rasteriser with Python bindings · server, PyTorch 2.7+, CUDA 12.8/13 · Apache-2.0 · no mesh/silhouette export described · **[direct]** https://github.com/nerfstudio-project/gsplat.
- **Nerfstudio** · training pipelines; inputs: images/video via COLMAP, Polycam (iOS LiDAR), KIRI, Record3D, Spectacular AI, Metashape, RealityCapture · "You must have an NVIDIA video card with CUDA" · Apache-2.0 · point-cloud export only on the README **[direct]** https://github.com/nerfstudio-project/nerfstudio.
- **Phone capture apps**: Scaniverse exports PLY/SPZ and processes on device; Polycam exports "splat PLY"; Luma exports a Gaussian-splat ZIP with a PLY inside **[via search]** (Scaniverse news page, Polycam help centre). None of their terms of service were readable; ownership/commercial terms **unverified**.
- **Does it help a silhouette model?** No. The twin needs, per piece class, a profile of revolution (radius as a function of height), i.e. 6 small arrays. A splat gives a view-dependent radiance field with no surface; extracting a silhouette means rendering it, which re-introduces a renderer. Measuring six pieces with a ruler, or fitting the profile from one calibrated side photo (the homography gives mm per pixel on the board plane), is cheaper and more accurate, and the plan already tests dims at ±20 % (`--dims-scale`). **Verdict: overkill** (the whole area).

## 5. Segmentation for piece silhouettes on the phone

Phone-browser timings for any of these under onnxruntime-web were **not found**; every published number is Core ML, QNN or desktop. Expect wasm to be 5 to 20× slower than the Core ML figures.

**Verdict versus frame differencing: differencing wins for the twin.** The twin compares a predicted change mask with an observed one; a 128 × 128 absolute difference after re-alignment is ~16 k subtractions and already produces the "observed" mask with the right semantics (what changed, including shadows). SAM-family masks would (a) cost 0.3 to 3 s per stable frame on a phone, (b) need a prompt per piece, which is what the twin is trying to infer, and (c) add 25 to 45 MB. Keep MobileSAM/EfficientSAM as an `eval/`-side tool to produce ground-truth silhouettes for tuning `lambda` and `--dims-scale`, where latency does not matter.

## 6. Tracking the board under camera wobble

- **OpenCV.js** exports `goodFeaturesToTrack`, `calcOpticalFlowPyrLK`, `calcOpticalFlowFarneback`, `findTransformECC`, `findHomography`, `estimateAffine2D`, `warpPerspective` **[direct]** (config file, §2); **`phaseCorrelate` is not exported**. The official tutorial `js_lucas_kanade` exists for `cv.calcOpticalFlowPyrLK` **[via search]**. Same 2 to 14 MB cost as §2. **Verdict: maybe**, only if §2 pulls OpenCV.js in anyway.
- **jsfeat (`inspirit/jsfeat`)** · pure JS: `optical_flow_lk`, FAST, YAPE, ORB, `motion_estimator` with RANSAC/LMedS over affine2d and homography2d kernels · browser · small · MIT · **last commit 2018-03-03**, 44 open issues **[direct]** https://github.com/inspirit/jsfeat. Unmaintained but self-contained and permissive; the LK and RANSAC-homography kernels are ~600 lines and could be vendored. **Verdict: maybe** (vendor the two kernels if the plan's `globalShift` ever needs sub-pixel multi-point tracking).
- **wasm-ar (`EdwardLu2018/wasm-ar`)** · ORB + homography, then Lucas-Kanade frame-to-frame, OpenCV compiled to wasm via `build_js.py`, WebGL2 grayscale, Web Workers · demo-grade, no releases, **no LICENSE file found** (404), commit history page empty **[direct]**. **Verdict: no** (reference for the "ORB when lost, LK otherwise" structure only).
- **Phase correlation in JS**: no maintained npm package found **[via search]**; the algorithm is one FFT pair on the 128 × 128 grey crop plus a peak search, and subpixel refinement by local DFT upsampling is the standard trick (pyxem docs) **[via search]**. **Verdict: hand-roll if `globalShift` (integer-pixel exhaustive search) proves too slow or too coarse; otherwise skip.**
- **Rust `optical-flow-lk` crate** (wasm-compatible) **[via search]** docs.rs. **Verdict: no** (adds a toolchain).

For a tripod that moves "a few pixels", the plan's exhaustive integer shift over ±4 px on a 128 × 128 crop is ~1.3 M byte-ops per frame and needs no library. The only reason to upgrade is rotation/scale drift, in which case re-running the RANSAC grid fit on fresh centroids (Task 2) is the right fix, not a tracker.

## 7. Existing open-source chess "digital twin" / AR chess projects (2023 to 2026)

No project found combines a physical-board camera with a 3D projective model of the pieces. Everything is 2D: detect board, map detections to squares through a homography, diff board states. The closest:

- **ArUco-Chess-Tracker (`atdotslash`, Python/OpenCV 4.7+, MIT, commits 2026-09-22 → 2026-09-29)** · ArUco marker on every piece base, corner markers 100 to 103 at a1/h1/a8/h8, "projective homography to map the board into a normalized [0, 8] × [0, 8] coordinate space", move detection by **frame differencing** with a 5-stable-frame buffer that ignores hands, ChArUco calibration wizard, TCP API for robots/engines **[direct]** https://github.com/atdotslash/ArUco-Chess-Tracker. Needs markers on the pieces, so not applicable, but its stable-frame gating matches our `StableFrame` design.
- **Play-online-chess-with-real-chess-board (`karayaman`, GPL-3.0, last commit 2025-10-05)** · webcam → online board; bundled `yolo_corner.onnx`, `cnn_piece.onnx`, `cnn_color.onnx`; empty-board corner calibration then start-position calibration; README does not address camera motion **[direct]** https://github.com/karayaman/Play-online-chess-with-real-chess-board.
- **chess-video-move-detection (`oliverfrost1`, MIT, last commit 2024-12-12)** · YOLOv11m-seg board polygon, YOLOv11l pieces, YOLOv11l **hand detector to drop occluded frames**; "If a piece disappears from one square and appears on another, it's considered a move"; lists "extreme camera angles or a moving camera" and "partially obscured pieces" as failure modes **[direct]** https://github.com/oliverfrost1/chess-video-move-detection. Those two failure modes are precisely what the twin's visibility term targets.
- **chessCamera (`VictorC55`, no licence stated, last commit 2026-10-16)** · YOLO11s-pose with four board-corner keypoints carrying visibility flags "so corners hidden behind pieces or hands stay usable", YOLOv8m 12-class pieces, single-image, no tracking, no 3D **[direct]** https://github.com/VictorC55/chessCamera.
- **fenshot (`scoriiu`, MIT, last commit 2026-10-16)** · screenshot → FEN fully client-side, onnxruntime-web wasm, 64-square CNN "~330k params, 1.3 MB ONNX", npm `@scoriiu/fenshot` **[direct]** https://github.com/scoriiu/fenshot. Screenshots only, but it is the one live example of our exact runtime stack (onnxruntime-web + wasm) in production.
- Older/other: ARChessAnalyzer (OpenCV + Caffe + Stockfish 9, pre-2024), JunkyDeveloper/AR-Chess (C++ marker AR), LiveChess2FEN, ChessVision (chose 2D pieces because 3D pieces defeated their image processing) **[via search]**. No WebXR/WebAR chess-on-a-physical-board project surfaced in two extended searches.

**Takeaway:** the twin is novel in this niche. Nobody has published the cylinder-projection trick, so there is no code to reuse; what can be reused is the consensus pipeline shape (stable frames, hand gating, per-square diffs), which the plan already has.

## Recommended stack for the twin

Minimum set, and why:

1. **Hand-rolled TypeScript geometry** (`focalFromVanishing`, `poseFromHomography`, `project`, cylinder hull fill): the maths is in the OpenCV homography tutorial source and fSpy's `solver.ts` (test against them, do not copy fSpy, it is GPL). Zero bytes, synchronous, testable with synthetic cameras.
2. **CPU integer ID buffer** instead of 30 separate masks: paint piece indices back-to-front into one `Int16Array(128*128)`; visibility and silhouettes come from the same pass. This is the three.js GPU-picking pattern transposed to the CPU, and avoids any WebGL readback on the phone.
3. **Frame differencing on the re-aligned 128 × 128 crop** for the observed mask (already planned). No segmentation model in the app.
4. **No new runtime dependency.** OpenCV.js is the only candidate that earns its place, and only if (a) the closed-form pose misses the 2° target in Task 3 tests, or (b) wobble turns out to include rotation. If (a), prefer a 40-line Gauss-Newton on reprojection error over an 81-point correspondence set before pulling in a 2 to 14 MB wasm.
5. **Offline only, in `eval/`:** MobileSAM or EfficientSAM (Apache-2.0) to produce ground-truth silhouettes on corpus frames for tuning `lambda` and checking `--dims-scale`; DA3-SMALL (Apache-2.0) as an independent focal/pose cross-check on a few tripod frames if `focalFromVanishing` and the phone's EXIF disagree.

Explicitly out: three.js/Babylon (readback cost, size), VGGT/MASt3R/DUSt3R/FoundationPose (server GPUs, mostly non-commercial), Gaussian splatting (no silhouettes without a renderer; a 6-number revolution profile per class is the better model), WebXR depth (no Safari, breaks the capture loop), EdgeSAM (non-commercial licence), SAM 3 (848M, custom licence).
